# Proposed interruption contract

**Trust direction approved for detailed design and implementation; no runtime implementation yet.** On 2026-10-17 local time (2026-10-18 UTC), Ross approved the recommendation below after independent review of proposal commit `0a9f8eca67808fdf2e4e380a2b83e839b0fad277`. Exact wire, enrollment and storage details remain design/validation obligations before activation. This document belongs to **tc-ach.2**, with independent trust review in **tc-ach.7**. It extends the request semantics in [SPEC.md](SPEC.md), consumes the [provider evidence](COMPATIBILITY.md), and does not replace their acceptance gates. The coordinator owns this shared contract; adapters and mobile consumers must not create competing versions.

Source basis: `6dfbc20a8e5d740a6b70a6fd5ed74c7efdfeac3e` on the pinned fork baseline. No supported fork release or deployed mixed-version frontier has been established. Names below marked proposed are design choices, not existing APIs.

Observed: the legacy payload contains a request ID and decision/policy/answer fields. It does not carry the required machine/backend/run/revision/action/device binding. Structured-question V1 validates answer shape and requires a live owner, but does not by itself add that complete binding. The coordinator's acknowledged completion awaits the agent-state write and then releases waiters; it does not wait for a native agent to consume the reply.

The development cancellation correction in **tc-ach.2.1** lets an owner-generated `canceled` completion release its exact waiter while a remote decision is awaiting that write acknowledgement. The late decision cannot resolve the retired waiter or apply its session-wide permission side effects; neighboring requests remain live. The serialized projection converges after the transport settles. [Composed cancellation coverage](../../apps/cli/src/agent/permissions/ProviderEnforcedPermissionHandler.cancellation.integration.test.ts) exercises success and failure of the delayed acknowledgement through the real session, router, store and coordinator. This correction does not add native request-event reconciliation, device authentication or provider-application acknowledgement.

`permissionResponseClaimV1` is an existing opaque presence fence: current store/coordinator code preserves or refuses claimed entries without interpreting that value. It is not an implemented device-authentication or complete single-use response protocol. Preserve its existing behavior; do not silently repurpose it as proof of the proposed contract.

## Caller-visible contract

The phone first receives a request projection, opens its current detail, and submits one allowed response against that exact detail. An expired notification only opens the inbox. It never carries an approval credential or directly performs an action.

Proposed shared schema placement: `packages/protocol/src/permissions/sessionInterruptionV1.ts`, exported through the package's existing public boundary. Proposed mutation name: `session.interruption.respond.v1`, registered through `SESSION_RPC_METHODS` and the existing session RPC router. These are new names for review, not source paths or methods that currently exist.

| Field | Authority and meaning |
|---|---|
| `v` | Explicit version 1; unknown versions cannot authorize an action |
| `machineId`, `backendInstanceId`, `sessionId`, `runId` | Bound by the local executing owner to the actual native backend and session incarnation, independently checked against the addressed session and authenticated connection scope |
| `requestId` | Native pending identity, or an adapter identity proven to address one particular native callback; never recovered from terminal display position |
| `revision`, `actionDigest` | Owner-issued freshness and canonical operation/choice binding; the response echoes the values for the displayed detail |
| `kind`, `allowedResponses` | Typed operation and provider-proven response capabilities; an ordinary message or answer cannot change permission policy |
| `operationId` | Client-generated identity for this decision attempt, bound to the complete request reference, response content and authenticated sender |
| authenticated device identity | Derived by the executing owner from an enrolled key and verified response proof, not accepted from an untrusted `deviceId` string or relay assertion; the direction is approved, with the detailed proof still to be implemented and verified |

The request's canonical action includes the actual structured operation/input or question/choices and the one-action scope being granted. Cosmetic notification text is not part of its authority. The digest must cover the canonical action that the owner will apply, including material choices and scope. The implementation must define one serialization/digest owner and provenance-backed vectors before adapter writers consume it; no secret, credential or arbitrary environment snapshot belongs in that action.

### Capture the action once

**Detailed design candidate, independently source-reviewed at `d012c90e25`; not implemented.** Create one validated, detached action snapshot at the live request owner, serialize it once, and retain that exact JSON string for the request revision. Reuse the protocol's [length-delimited byte framing and domain-separated digest](../../packages/protocol/src/crypto/canonicalDigest.ts) over its UTF-8 bytes. The phone verifies the owner-authenticated bytes before parsing them for display; it does not rebuild JSON from a display projection to verify the signature. The native response path consumes the same captured action and mapping, or invalidates the request when they change. This avoids a second sorted-JSON canonicalizer and preserves one authority for display and dispatch. A detached object or a shared `Uint8Array` is still mutable; neither alone establishes the required retained snapshot.

Capture all material operation/input, question text and descriptions, choice values, selection/freeform rules, defaults, validation constraints and one-action scope. Display-only questions are insufficient. The existing [OpenCode V2 form projection](../../apps/cli/src/backends/opencode/server/openCodeV2Forms.ts) keeps native field keys, label-to-value mappings, hidden defaults, conditions, types and declaration order separately from its visible questions. [The current reply client](../../apps/cli/src/backends/opencode/server/client.ts) reads that cached projection when constructing the native answer. Signing only published questions while retaining that later cache lookup would leave a different action available at dispatch.

Validate the complete supported typed action **before** lossy projection. The existing OpenCode projector filters malformed options, conditions and defaults and skips unknown field types; it is not the new contract's admission validator. Unsupported material data makes the companion response unavailable rather than silently approving a partial interpretation. The existing native terminal remains the local response path. Duplicate field/question identities or ambiguous choice mappings also need explicit rejection or a provider-proven exact representation; legitimate record keys such as `__proto__` must remain data.

Reuse or extract the structural snapshot logic in [normalizeAskUserQuestionInput.ts](../../apps/cli/src/agent/questions/normalizeAskUserQuestionInput.ts) as part of the first consumed implementation, instead of adding a competing walker. It rejects cycles, accessors, non-JSON values and properties that JSON would drop, and copies own data into safe records. Its question-specific limits and descriptor policy must stay with questions; non-question permission inputs currently pass through unchanged. The shared [structured-question schemas](../../packages/protocol/src/tools/structuredQuestionAnswersV1.ts) remain the answer/descriptor owner, but their normalized result deliberately omits provider extras and is not the complete action snapshot.

Only the validated-object producer may issue snapshot JSON; caller-supplied strings are not prevalidated snapshots. That producer cannot emit duplicate JSON member names, so this choice does not require a new duplicate-key parser. It does not certify arbitrary external JSON whose duplicate members were already lost during parsing. Preserve absent, null, empty and explicit false as distinct values. Preserve whitespace and Unicode without normalization.

The first supported action/response schema must apply these value rules. They are **detailed design requirements, not implemented guarantees**. Source review against OpenCode `2.0.15` (`6f3639d82ed0760091792189b78f8eeb44f699b1`, `packages/core/src/form.ts` and `packages/protocol/openapi.json`) and Node `22.14.0` serialization checks establish the distinctions below; Android byte/display parity remains unverified.

| Value boundary | Required interpretation |
|---|---|
| Native JSON numbers | Bind the finite binary64 value admitted by the provider schema. OpenCode's native form validator checks finiteness and, for integers, `Number.isInteger`; it does not require safe integers. Do not claim preservation of original decimal spelling or arbitrary-precision integers after native JSON parsing. Proof counters/revisions separately need an exact integer representation |
| Non-finite numbers and negative zero | Reject non-finite values. Reject `-0` for generic capture unless the provider's typed contract proves and performs an equivalent normalization before capture; JSON serialization alone changes it to `0` |
| Encoded numeric defaults/constraints | OpenCode's published numeric fields also admit the strings `Infinity`, `-Infinity` and `NaN`. The current projector omits these numeric string defaults/constraints; the native codec semantics have not been verified. Such material numeric forms are unavailable for companion response until that codec is supported and verified. Ordinary string answers with these spellings remain strings |
| JSON string contents | Retain JSON serialization's escaped lone-surrogate code units; encoding that retained JSON text preserves them. Do not UTF-8-encode raw string values separately and substitute those bytes into the action proof. The consumed phone/provider path must prove this round trip before admitting such values |
| Direct proof strings | Validate Unicode scalar values before passing raw strings to the framing helper. `TextEncoder` replaces a lone surrogate with U+FFFD, so unvalidated raw strings would alias distinct identities. This validation does not normalize valid Unicode |
| Verified action bytes | Verify the exact owner-issued bytes, then strictly decode UTF-8 and parse those same bytes for display. Reject invalid encoding; do not verify one representation and parse a different transport string. Existing HTTP/SSE decoding is not original-wire-byte preservation; capture binds the validated decoded native value |

Construct and validate the actual typed native response from the captured action **before confirmation/signing**. A selected option identifies its declared native value; custom text remains literal text. The current OpenCode label-row answer cannot distinguish selecting label `Europe` (native value `eu-west`) from typing the custom string `Europe`. Reusing that ambiguous row as the signed response would not satisfy this contract. Its numeric `Number(value)` coercion also accepts hexadecimal spelling and rounds large integers; do not silently inherit those conversions as approval semantics. The response schema and phone confirmation must bind the resolved native value without a later reinterpretation through mutable labels, caches or defaults.

This snapshot supplies action bytes, not the entire authenticated reference. The distinct proof builders must also bind the request/run/revision, allowed response and scope, authenticated authority, and operation identity as appropriate, with explicit field order and optional-field presence. Existing registration or generic serialization helpers do not define that proof. Required discriminating vectors include identical display labels with changed native mappings, changed hidden defaults/conditions, post-display mutation, unsupported material fields, scalar/Unicode boundaries, and verified display through the captured native dispatch. Existing question/form tests provide reusable cases, not evidence that the new signed composition works.

### Incarnation and response scope

`runId` identifies the native execution incarnation, not a socket connection, transcript, PID alone or a second process resuming history. A relay or phone reconnect must not invent a new run. If a restarted connector cannot establish the native instance and its current pending inventory, it exposes unknown/unavailable state and accepts no earlier response until reconciliation succeeds. The local native terminal remains usable. The runtime identity producer belongs with the existing session/terminal host; this proposal does not mandate another process, database or persistent lease.

A permission response grants or denies only one pending action. Explicit broader policy changes stay a separate deliberate operation and are outside the initial companion response. Questions reuse `StructuredQuestionAnswersV1`; plan review and input-required errors need explicit provider mappings before becoming actionable. Ordinary messages use the existing message/input owner and its draft-safe queue, never a permission decision or unbound terminal key.

## Validation and arbitration

At the executing owner, before any native effect:

1. Validate the versioned shape and trusted sender authorization for the addressed machine/session. Check revocation through the approved authentication owner.
2. Find the locally owned live pending request. A persisted relay projection or historical cached decision is insufficient to create native authority.
3. Compare every binding field, revision, action digest, response kind and allowed choice with the owner's current request. Reject a mismatch without falling back to legacy RPC or keystrokes.
4. Reuse the request coordinator's admission point for competing remote attempts. A repeated operation with identical sender and canonical content observes its prior result; reusing its identity with different content is rejected. Do not dispatch twice after an uncertain result.
5. Submit to the same native callback/API and observe the provider's authoritative outcome. Local and remote competitors must be arbitrated by that native authority, or by a host proven to observe both paths. A phone lock or CLI-only flag cannot fence a local terminal response.

Operation memory lives with the current request/run owner and its existing lifecycle, not in a new account-wide relay ledger. After that authority is gone, old operations are stale or unverifiable; they are not automatically replayed. Retention, expiry and storage bounds must follow the real owner/provider contract, not a guessed timeout or TTL introduced by this proposal.

Changing an operation or choices invalidates its earlier display binding. Native resolution/cancellation removes that pending authority and updates the existing projection. If an adapter cannot reliably observe local deny/cancel or distinguish repeated identical requests, its remote decision capability remains unavailable. It must not compensate with terminal-text parsing or automatic approval.

## Results and recovery

| Result | What may be shown or done |
|---|---|
| `received` | The executing owner admitted this operation; it is not yet a successful native response |
| `applied` | The native authority confirmed this response for this pending request; a tool's later success/failure is a separate event |
| `resolved` | The request is no longer pending according to native evidence; do not attribute the winning response unless that evidence identifies it |
| `rejected` | Typed unsupported, unauthorized, stale, mismatched, expired or already-resolved result; no new native effect from this operation |
| `indeterminate` | Delivery may have reached the provider but acknowledgement/reconciliation cannot establish the result; disable automatic retries and show the uncertainty |

The proposed public lifecycle is `pending` → `resolving` → a native-supported terminal outcome, with cancellation, expiry, supersession and indeterminate states distinguished. A relay receipt, socket write, completed-state record or `serverRequest/resolved` notification alone must not be promoted into proof that this particular answer was applied.

Reopening the app refreshes the existing pending projection and reconciles against the reachable native owner before enabling a response. Keep delivery deduplication separate from native decision deduplication. Offline decisions are not queued for later automatic execution. When reconciliation is unavailable, retain visible unknown/disconnected state and local terminal control.

## Compatibility and activation

This is a new capability, not a replacement of all upstream session modes. Existing upstream flows can remain where they cannot bypass the companion authority described below; a session-mode label alone does not establish that isolation. For a companion request, both the UI and executing owner must explicitly support this contract and the required native capabilities; missing/malformed support fails closed. Keep provider facts in the canonical agent catalog/provider leaves and feature decisions in their existing owners.

The new client must not silently retry the legacy permission method when the versioned method is missing. A new receiver must reject a legacy response against a companion-bound request, including the legacy structured-question route. Reader support cannot be inferred from a version string alone. A session listing or transcript may remain readable without permission capability.

Keep the new request schema in the existing agent-state/projection corridor; the exact carrier and old-reader behavior require compatibility fixtures before activation. Do not dual-write two independently actionable representations. A historical request read from storage cannot become a live request merely because a newer client can parse it. Unknown opaque fences retain their current fail-closed treatment.

Required directions before enabling the capability: new UI to older CLI safely reports unsupported; older UI to new companion runtime cannot bypass binding through legacy methods; current readers handle historical persisted requests as non-authoritative until reconciled. An older relay may already transport the new encrypted operation without understanding it; establish its actual routing and authorization behavior instead of rejecting it solely by version. Cross-account delegation has additional method authorization and needs its own disposition. Rollback into an older executing runtime is not certified by the current source. Resolve exact supported immutable component/artifact baselines and any reachable stored-data direction under [the compatibility policy](../compatibility.md) before implementation claims support. No database migration or deployed compatibility transition is authorized by this draft.

## Approved trust direction

**Observed gap:** [server socket authentication](../../apps/server/sources/app/api/socket.ts) retains the verified account ID. [RPC forwarding](../../apps/server/sources/app/api/socket/rpcHandler.ts) sends method, params and transport/operation authorization, without an authenticated phone principal. [UI session RPC](../../apps/ui/sources/sync/api/session/apiSocket.ts) and [CLI RPC handling](../../apps/cli/src/api/rpc/RpcHandlerManager.ts) support both encrypted and raw plain params. Neither account access nor possession of a content key identifies a particular phone. The inspected token-cache invalidation and machine-revocation paths do not establish phone revocation.

**Approved direction, not implemented behavior:** add locally enrolled device proofs while retaining existing content encryption. The executing computer remains the authority for enrollment, authorization and revocation. A new device must be explicitly enrolled on each computer through an authenticated local pairing flow that binds the intended machine/request verification key and phone public key. A relay-supplied label, recovered account key or unauthenticated legacy pairing response cannot enroll a device.

The phone must verify the executing owner's authenticated request detail before showing an actionable control. Its device proof must bind the complete response, request reference, operation ID and one-action scope. The executing owner verifies that proof against its current enrolled-device authorization before native dispatch. Shared content-key possession alone does not prove request origin, particularly after a revoked phone retains old content keys. Define distinct typed proof purposes for request detail and response; do not reuse machine-registration signatures as approval signatures. This proposal adds authentication, not a new encryption cipher or a relay permission authority.

The same owner authentication must cover current-state reconciliation and response results. A valid historical signature does not prove that an item is still pending, and a retained content key must not let its holder fabricate an apparently successful result. Correlate an authenticated current-state reply with the phone's query before enabling a response; bind an authenticated result to the exact request and operation. The native owner still revalidates at dispatch because a local answer can race any displayed snapshot. Specify that correlation at the existing protocol owner before activation; do not substitute an arbitrary approval lifetime or a relay receipt. Unreachable or unverifiable state remains non-actionable.

Initial companion control would require authenticated request details **and** the existing encrypted session transport/projection. Plain sessions would have no companion mutation capability, including approvals, structured answers and ordinary remote input. A signed response alone cannot protect a plain displayed action from relay substitution. Plain companion control requires a separate reviewed confidentiality/request-authentication decision; it is not silently enabled by adding a signature field.

**Activation prerequisite: close alternate remote authority.** [Session registration](../../apps/cli/src/api/session/sessionClient.ts) and [machine registration](../../apps/cli/src/api/apiMachine.ts) install [shared handlers](../../apps/cli/src/rpc/handlers/registerSessionHandlers.ts), including [generic command execution](../../apps/cli/src/rpc/handlers/bash.ts). The session default is OS-user access, and the current machine RPC authorizer does not apply device authentication to those methods. A revoked phone retaining account credentials/content keys could use that route to affect the native process or local trust material. This is a source-derived bypass, not an executed exploit; local file ACLs cannot isolate a process from commands running as its own user.

Before activating companion control, every reachable remote path able to execute code, control the native session, or read/change its trust material must enforce the same approved device authority or be proven unavailable/isolated. Reuse the existing RPC authorization boundary and inventory terminal, filesystem, transfer and metadata/control bypasses. The first pilot may leave unrelated privileged handlers unavailable in the companion runtime rather than implement their new authorization immediately. A legacy session/daemon reachable with the same retained credentials and OS-user authority cannot be waved through as unrelated. Preserving an existing upstream flow is conditional on this boundary holding; this draft does not authorize changes to existing user installations or a general upstream authentication rewrite.

Revocation is enforced by each executing computer before its next dispatch. A device revoked on one computer is not automatically proved revoked elsewhere: the UI must identify each enrolled computer and show an unreachable/unconfirmed revocation explicitly. Local terminal revocation must remain available without the relay or lost phone. Re-enrollment, recovery and any stronger cross-computer revocation promise require explicit semantics; account recovery must not silently restore a revoked device's approval authority.

Reuse these owners where their contracts fit. Do not invent another global identity registry, copy recovery/content keys into a signing role, or introduce a production dependency without review. The exact proof bytes, enrollment exchange, protected local trust storage and revocation update path remain design/validation obligations before a consumed implementation. Ordinary input keeps its existing queue and separate semantics but must consume the same verified device authority; it cannot be an unsigned bypass.

Use separate typed proof-byte builders with explicit purposes; the existing machine-registration JSON builder is specific to registration. Select an enrolled verification key from local authority rather than trusting a key supplied by the response. Normalize key identity by decoded bytes or one canonical encoding: the shared base64 decoder is permissive, so arbitrary text spellings must not create separate enrolled identities. Protected atomic file replacement establishes neither serialized enrollment/revocation nor cache invalidation across concurrent session hosts; the ordering below is additional proposed behavior. No new process boundary is selected by this document.

Account-only or relay-asserted device identity does **not** satisfy the current SPEC. Choosing either would require an explicit change to the approved trust requirement. Ross approved new device authentication, authenticated local enrollment and per-computer revocation, with encrypted-only initial companion control and the alternate-authority activation prerequisite. That grant authorizes detailed design and implementation within this boundary; independent security review and native validation remain required before activation. It does not authorize changes to existing user installations, new production dependencies, credentialed/paid provider tests, deployment, or weaker controls.

## Enrollment scope decision

**Approved clarification; the earlier ambiguous scope is SUPERSEDED_BY_APPROVED_AMENDMENT.** Ross approved per-installation revocation after independent source review. The existing [CLI home owner](../../apps/cli/src/configuration.ts) selects one installation identity beneath the resolved CLI home (`HAPPIER_HOME_DIR` or its default). The [identity store](../../apps/cli/src/daemon/identity/store.ts) creates a random installation ID; it does not identify physical hardware. [Machine registration selection](../../apps/cli/src/auth/machineIdentitySettings.ts) further scopes routing IDs by server and account. Therefore neither a hostname nor a current `machineId` establishes one revocation authority covering all independent installations on a desktop.

Use one protected companion authority per explicitly enrolled CLI installation, shared by its session processes and associated with its installation identity. Keep server/account/machine routing bindings and distinct provider configurations; do not partition revocation by a mutable registration ID. Present independently enrolled installations separately in device management, even when their computer names match. Revoking a phone at one installation blocks that phone's later remote dispatches there; it does not revoke that phone at another installation on the same desktop. This is the approved meaning of “per-computer revocation” for this design.

Enrollment is explicit, missing or mismatched trust state cannot recreate authority, and account recovery or machine re-registration cannot undo revocation. Separate CLI homes under the same OS user do not isolate legacy command/file/control access: the alternate-authority activation prerequisite above still applies across them. This records a design decision; no installation, credential or runtime behavior has changed.

## Local revocation and dispatch ordering

**Detailed design candidate, independently source-reviewed; not implemented or validated.** Reuse [withJsonOwnerFileLock](../../apps/cli/src/utils/fs/jsonOwnerFileLock.ts) around one protected trust store for each enrolled computer authority. This existing primitive preserves a known-live foreign process rather than stealing its lock by age, and holds exclusion until its supplied effect settles. Initialize and verify the protected parent first; keep the lock pathname outside any atomically replaced file. The store identity/location and its relationship to runtime profiles must be explicit before implementation: separate profiles must not silently promise shared revocation. An installed daemon is not required by this choice. The existing daemon master token does not authenticate a phone, and the settings/installation-identity creation locks do not supply this ordering.

Enrollment and local revocation acquire the same lock, read and strictly validate current protected state, apply the authenticated local change, and complete protected replacement before releasing. Confirm revocation only after successful completion. Remote dispatch acquires that lock, freshly verifies current device authority and the signed request/response binding, rechecks the existing coordinator's live pending request, and initiates the exact provider-bound response before release. Queued ordinary input performs this check at delivery, not just at queue admission. Missing, malformed, unreadable or unsupported trust state denies remote dispatch; it must not silently recreate enrollment.

This orders successful revocation against **native enqueue**, not later native application. A response already handed to the provider may finish after revocation; later dispatches must fail. Provider acknowledgement and relay projection occur outside the trust lock. Do not hold it across human interaction, relay acknowledgement or tool execution, and do not copy unrelated lock timeouts into approval policy. Acquisition uses the applicable caller cancellation/budget; no unlocked fallback is allowed. Failure after possible enqueue, including lock-release failure, retains an uncertain operation outcome and cannot trigger automatic redispatch.

The current request coordinator cannot establish this boundary by wrapping its existing completion call. Its `completeResponseWithAck` waits for an agent-state write acknowledgement before resolving waiters. Actual [OpenCode permission transmission](../../apps/cli/src/backends/opencode/server/runtime.ts) and [Claude hook HTTP response](../../apps/cli/src/backends/claude/utils/startHookServer.ts) occur afterward. A consumed implementation must extend the existing coordinator/provider boundary so the lock covers actual enqueue; waiter resolution and a projection ACK are insufficient. Keep operation deduplication and cancellation at the existing request owner, with native authority still arbitrating local/remote competitors.

Required evidence includes two session processes racing revocation against enqueue, cancellation while awaiting authorization, duplicate/conflicting operations, post-enqueue acknowledgement loss and lock-release failure. Validate real Windows protected state/ACLs, atomic replacement and lock recovery before activation. Existing [lock tests](../../apps/cli/src/utils/fs/jsonOwnerFileLock.test.ts) and protected-state tests are reusable coverage, not evidence that this new composition works. Legacy privileged-path isolation, exact proof/schema bytes, provider enqueue semantics and physical-Android revocation remain open gates.
